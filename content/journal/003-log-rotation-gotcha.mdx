We were building a dashboard for our testnet validator, poking around to check
which metrics were real. That is when we noticed `solana-validator.log` had
already grown to 3.8 GB, and by the next day it was pushing 7 GB.

That is how we learned about log rotation, and why we had missed it: we followed
a setup script, and log rotation lived in a different section that we skipped.
The upside is that watching our own metrics surfaced the problem fast.

## What log rotation does

Log rotation keeps log files from growing without bound. Instead of one endless
file, you get a series of smaller ones. Each day yesterday's log is saved and a
fresh one starts; after a week or so the oldest is deleted. It looks like this:

```text
solana-validator.log      today's log
solana-validator.log.1    yesterday
solana-validator.log.2    two days ago
solana-validator.log.3    three days ago
solana-validator.log.4    four days ago
... and so on
```

A tool called logrotate handles this. It runs once a day: renames yesterday's
file, starts a new one, deletes the oldest. You set the rules in a config file
and logrotate does the rest.

## Why rename alone is not enough

Files in Unix-like systems have two parts: the data (the actual bytes) and the
metadata (size, permissions, owner, timestamps, and crucially, pointers to where
the data blocks live on disk). That metadata blob is the inode. It has a number,
but it does not store the filename.

A filename is just a mapping to an inode number. You can have multiple names
pointing at the same inode, or zero names pointing at a live inode (a deleted but
still open file).

The other piece is the file descriptor (fd). When a process calls
`open("sol.log")`, the kernel walks the directory, finds the inode, and hands the
process back a small integer, the fd (0, 1, 2, 3...). Think of it as a claim
ticket. From that point on, every `read()`/`write()` the process does uses that
fd number, and the kernel resolves it internally to "inode 48213, current offset
X." The process never looks up the name again for that handle.

This is why `rename()` alone does not help: it only edits the name, but a process
holding an fd is bound to the inode, not the name. Rename the file and the
validator keeps writing to the same inode, now under a different name.

So logrotate does not only rename the file, it also tells the validator to reopen
its log. It does this with a signal called USR1. In the config you will see:

```text
postrotate
   systemctl kill -s USR1 sol.service
endscript
```

Despite the scary "kill" word, this just means "send USR1." When the validator
gets it, it starts writing to the new log file.

This works because SIGUSR1 is the trigger that makes the validator voluntarily
drop the fd and call `open()` again, which is the only way to get a new fd
pointing at the new inode.

## The permissions snag

This is a common one; the Anza docs cover it:
[https://docs.anza.xyz/operations/guides/validator-start](https://docs.anza.xyz/operations/guides/validator-start)

We set up the config and ran a dry run. It failed at first:

```text
error: skipping "/home/sol/logs/solana-validator.log" because parent directory
has insecure permissions ... Set "su" directive in config file to tell logrotate
which user/group should be used for rotation.
```

Our logs folder was owned by the sol user, not root. By default, logrotate will
not touch files it does not own. The fix is to add `su sol sol` to the config so
rotation runs as the right user. Here is what worked:

```text
/home/sol/logs/solana-validator.log {
   su sol sol
   rotate 7
   daily
   missingok
   postrotate
       systemctl kill -s USR1 sol.service
   endscript
}
```

After that, the dry run passed. The daily timer was already running, so
everything started rotating on schedule.

## Did it work?

A week later, we checked:

```text
solana-validator.log       2.4G  Jul 14 16:46   (today)
solana-validator.log.1     3.4G  Jul 14 00:00
solana-validator.log.2     3.4G  Jul 13 00:00
solana-validator.log.3     3.4G  Jul 12 00:00
solana-validator.log.4     3.3G  Jul 11 00:00
solana-validator.log.5     3.4G  Jul 10 00:00
solana-validator.log.6     8.0G  Jul  9 00:00   (the old backlog)
```

Each rotated file is stamped at exactly midnight. The current log keeps growing,
and the old ones are frozen. That is how we know the rotation and the signal are
working.
