We didn’t plan for this. We were just building a dashboard for our testnet
validator, poking around to check which metrics were real. That’s when we
noticed a file growing too big. The file `solana-validator.log` was already at
3.8 GB, and the next day it was pushing to 7 GB.

This is how we got to know about log rotation and why we missed it.

The reason we missed it is low-key silly, but that's how we grow, right?

We followed a script while setting up the validator, and log rotation was in a
different section altogether. It got missed, but the good thing is that we check
our metrics and were able to find this problem pretty quickly.

## What Log Rotation Does

In plain English: log rotation keeps our log files from growing out of control.
Instead of one endless file, we get a series of smaller files. Each day,
yesterday’s log is saved, and a fresh one starts. After a week or so, the oldest
one is deleted. It looks like this:

```text
solana-validator.log      today’s log
solana-validator.log.1    yesterday
solana-validator.log.2    two days ago
... and so on
```

A tool called logrotate handles this. It runs once a day, renames yesterday’s
file, starts a new one, and deletes the oldest. We set the rules in a config
file, and logrotate does the rest.

## The Interesting Stuff

Here’s where it gets interesting. Files in Unix-like systems have two parts: the
data (the actual bytes) and the metadata (size, permissions, owner, timestamps,
and crucially, pointers to where the data blocks live on disk). That metadata
blob is the inode. It has a number, but it does not store the filename.

A name of a file is just a mapping to an inode number. We can have multiple names
pointing at the same inode number or zero names pointing at a live inode (a
deleted but still open file).

One more thing to understand here is the File Descriptor (fd). When a process
calls `open("sol.log")`, the kernel walks the directory, finds the inode, and
hands the process back a small integer — the fd (0, 1, 2, 3...). Think of it as
a claim ticket / handle. From that point on, every `read()`/`write()` the process
does uses that fd number, and the kernel resolves it internally to "inode 48213,
current offset X." The process never looks up the name again for that handle.

Why this matters for our logrotate case is that `rename()` only edits the name; a
process holding an fd is bound to the inode, not the name. So just renaming our
file to a different name will not do the trick. It will continue to write to the
same log file, albeit with a different name now.

To fix this, logrotate doesn’t just rename the file — it also tells the
validator to reopen its log file. It does this by sending it a special signal
called USR1. In the config, you’ll see:

```text
postrotate
   systemctl kill -s USR1 sol.service
endscript
```

Despite the scary “kill” word, this just means “send USR1.” When the validator
gets it, it starts writing to the new log file. Problem solved.

This works because SIGUSR1 is the trigger that makes the validator voluntarily
drop the fd and call `open()` again — which is the only way to get a new fd
pointing at the new inode.

## Common issue

Turns out, lots of people have hit this issue. The Anza docs have a guide for
it: [https://docs.anza.xyz/operations/guides/validator-start](https://docs.anza.xyz/operations/guides/validator-start)

We set up the config and ran a dry run. It failed at first:

```text
error: skipping "/home/sol/logs/solana-validator.log" because parent directory
has insecure permissions ... Set "su" directive in config file to tell logrotate
which user/group should be used for rotation.
```

Our logs folder was owned by the sol user, not root. By default, logrotate
doesn’t want to mess with files it doesn’t own. The fix? Add `su sol sol` to the
config to run rotation as the right user. Here’s what worked:

```text
/home/sol/logs/solana-validator.log {
   su sol sol
   rotate 7
   daily
   missingok
   postrotate
       systemctl kill -s USR1 sol.service
   endscript
}
```

After that, the dry run passed. The daily timer was already running, so
everything started rotating on schedule.

## Did It Work?

A week later, we checked:

```text
solana-validator.log       2.4G  Jul 14 16:46   (today)
solana-validator.log.1     3.4G  Jul 14 00:00
solana-validator.log.2     3.4G  Jul 13 00:00
solana-validator.log.3     3.4G  Jul 12 00:00
solana-validator.log.4     3.3G  Jul 11 00:00
solana-validator.log.5     3.4G  Jul 10 00:00
solana-validator.log.6     8.0G  Jul  9 00:00   (the old backlog)
```

Each rotated file is stamped at exactly midnight. The current log keeps growing,
and the old ones are frozen. That’s how we know the log rotation and signal are
working.
